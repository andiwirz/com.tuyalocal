Cloud-assisted DP detection

Datenpunkte mit Hilfe der Cloud erkennen

Once your Cloud Lookup credentials have been saved here, pairing gets noticeably more accurate. The local connection only ever sees raw DP numbers and values, so the app has to guess what each one means from the value shape. The cloud specification instead supplies the manufacturer's own name per DP — envhumid, windspeed, work_state, bright_value and so on — which is matched directly.

Sobald Ihre Zugangsdaten für die Cloud-Suche hier gespeichert sind, wird das Anlernen merklich genauer. Die lokale Verbindung sieht immer nur rohe Datenpunktnummern und Werte, also muss die App aus der Gestalt des Werts erraten, was er bedeutet. Die Cloud-Spezifikation liefert stattdessen den Namen, den der Hersteller selbst vergeben hat — envhumid, windspeed, work_state, bright_value und so fort —, und der wird direkt zugeordnet.

This mainly helps devices whose enums use plain numbers (0 / 1) instead of names, where value-shape guessing has nothing to go on, and it reads the full list of allowed values for mode and fan-speed pickers rather than just the one value the device happens to be reporting at that moment. It is entirely optional — pairing works without it, you may just have to correct a few DP numbers by hand afterwards.

Das hilft vor allem Geräten, deren Aufzählungen blosse Zahlen benutzen (0 / 1) statt Namen — dort hat das Raten an der Gestalt nichts, woran es sich halten könnte. Ausserdem liest es die vollständige Liste der erlaubten Werte für Betriebsart und Lüfterstufe aus, statt nur den einen Wert, den das Gerät gerade meldet. Es ist völlig freiwillig: Anlernen geht auch ohne, nur müssen Sie danach vielleicht ein paar Datenpunktnummern von Hand richtigstellen.

Enum values are matched exactly

Aufzählungswerte werden genau verglichen

Mode and fan-speed settings hold the tokens the device itself uses, and the comparison is literal — case included. A device whose modes are Heat,Cool,Auto rejects heat,cool,auto, and the symptom is deceptive: the command appears to go through, then the device snaps straight back to its previous mode. Devices seen in the wild use cold,wet,wind,hot instead of cool/dry/fan/heat, or bheat,eheat,sheat,bcool,ecool,scool,auto for boost/eco/silent variants. Read the exact tokens from the DP specification in Cloud Lookup and copy them verbatim into mode_values / fan_speed_values. With Cloud Lookup credentials saved this is filled in automatically at pairing.

In den Einstellungen für Betriebsart und Lüfterstufe stehen die Wörter, die das Gerät selbst benutzt, und verglichen wird wörtlich — samt Gross- und Kleinschreibung. Ein Gerät mit den Betriebsarten Heat,Cool,Auto weist heat,cool,auto zurück, und das Symptom führt in die Irre: der Befehl scheint durchzugehen, dann springt das Gerät sofort in seine vorherige Betriebsart zurück. Geräte aus der Praxis benutzen cold,wet,wind,hot statt cool/dry/fan/heat, oder bheat,eheat,sheat,bcool,ecool,scool,auto für die Boost-, Eco- und Leise-Varianten. Lesen Sie die genauen Wörter in der DP-Spezifikation der Cloud-Suche ab und übertragen Sie sie wortgetreu nach mode_values / fan_speed_values. Sind die Zugangsdaten der Cloud-Suche gespeichert, geschieht das beim Anlernen von selbst.

Find the IP address

Die IP-Adresse finden

Use Scan Network in the pairing wizard, or check your router's DHCP table. Either way, assign a static IP / DHCP reservation so it never changes.

Im Anlern-Assistenten Netzwerk durchsuchen benutzen oder in der DHCP-Tabelle Ihres Routers nachsehen. In beiden Fällen sollten Sie eine feste IP oder eine DHCP-Reservierung vergeben, damit sie sich nie ändert.

Matching an IP to the right device is the harder half. Tuya devices report almost no hostname: older ESP-based ones appear as ESP_ plus the last six characters of their MAC, newer ones as wlan0, and the newest as lwip1 — so eight devices show up as eight identical wlan0 entries. Take the MAC address from the Tuya / Smart Life app under the device's Device info and match on that. Assigning the wrong IP produces a device that connects to something and then never responds.
Die IP dem richtigen Gerät zuzuordnen ist die schwierigere Hälfte. Tuya-Geräte melden fast keinen Rechnernamen: ältere auf ESP-Basis erscheinen als ESP_ plus die letzten sechs Zeichen ihrer MAC-Adresse, neuere als wlan0, die neuesten als lwip1 — acht Geräte stehen also als acht gleichlautende wlan0 da. Nehmen Sie die MAC-Adresse aus der Tuya- oder Smart-Life-App unter Geräteinformationen und ordnen Sie danach zu. Eine falsch vergebene IP ergibt ein Gerät, das sich mit irgendetwas verbindet und dann nie antwortet.

The scan works in two passes: it first listens six seconds for the announcements Tuya devices broadcast by themselves (UDP 6666/6667), then probes every address in your subnet on TCP 6668. On a normal home network that takes around ten seconds. The second pass is skipped on subnets larger than 2046 addresses, where probing every host would take minutes — devices there are only found if they announce themselves.

Die Suche läuft in zwei Durchgängen: sechs Sekunden lang hört sie auf die Rundrufe, die Tuya-Geräte von selbst aussenden (UDP 6666/6667), dann klopft sie jede Adresse Ihres Teilnetzes auf TCP 6668 ab. In einem gewöhnlichen Heimnetz dauert das rund zehn Sekunden. Der zweite Durchgang entfällt bei Teilnetzen mit mehr als 2046 Adressen, wo das Abklopfen jedes Rechners Minuten bräuchte — dort werden nur Geräte gefunden, die sich selbst melden.

Can this device be controlled locally at all?

Lässt sich dieses Gerät überhaupt lokal steuern?

Worth two minutes before spending an evening on settings. Local control needs the device to be listening on TCP 6668 (occasionally 6667). Point any port scanner — Advanced Port Scanner, a phone network-analyser app, nmap — at the device's IP and check those two ports.

Zwei Minuten, die sich lohnen, bevor Sie einen Abend in Einstellungen stecken. Lokale Steuerung setzt voraus, dass das Gerät auf TCP 6668 lauscht (gelegentlich 6667). Richten Sie irgendeinen Portscanner — Advanced Port Scanner, eine Netzwerk-App auf dem Telefon, nmap — auf die IP des Geräts und prüfen Sie diese zwei Ports.

Open means the device speaks the local protocol and any failure from here is a matter of key, protocol version or DP mapping. Both closed means it does not, and nothing in this app can change that — some devices sold as Tuya are Matter or cloud-only under the hood and simply have no local port. Users have chased such a device for weeks before running this check.

Offen heisst: das Gerät spricht das lokale Protokoll, und jeder Fehlschlag von hier an ist eine Frage des Schlüssels, der Protokollversion oder der Datenpunkt-Zuordnung. Beide geschlossen heisst: es spricht es nicht, und daran kann diese App nichts ändern — manches, was als Tuya verkauft wird, ist unter der Haube Matter oder reines Cloud-Gerät und hat schlicht keinen lokalen Port. Es hat Benutzer gegeben, die wochenlang hinter einem solchen Gerät her waren, bevor sie diese Prüfung machten.

Known to be impossible locally, whatever the settings say:
  • Battery sensors in deep sleep — door, motion, smoke, temperature/humidity sensors switch their radio off between reports. There is no window in which to connect, and the cloud sees them only because the device pushes to Tuya itself.
  • Bluetooth devices behind a Tuya gateway — the gateway proxies them to the cloud, not over the local protocol, and most models accept only one to three connections in total.
  • Cameras and video doorbells — the video stream is a proprietary peer-to-peer protocol. Ring and motion events over the local connection can work; the picture cannot. For the stream, use an ONVIF app if the device supports it.
Lokal erwiesenermassen unmöglich, was auch immer die Einstellungen sagen:
  • Batteriesensoren im Tiefschlaf — Tür-, Bewegungs-, Rauch- sowie Temperatur- und Feuchtesensoren schalten ihren Funk zwischen zwei Meldungen ab. Es gibt kein Zeitfenster, in dem man sich verbinden könnte, und die Cloud sieht sie nur, weil das Gerät von sich aus zu Tuya sendet.
  • Bluetooth-Geräte hinter einem Tuya-Gateway — das Gateway reicht sie an die Cloud weiter, nicht über das lokale Protokoll, und die meisten Modelle nehmen insgesamt nur ein bis drei Verbindungen an.
  • Kameras und Video-Türklingeln — der Videostrom läuft über ein herstellereigenes Peer-to-Peer-Protokoll. Klingel- und Bewegungsereignisse über die lokale Verbindung können gehen, das Bild nicht. Für den Strom eine ONVIF-App benutzen, sofern das Gerät es unterstützt.

Reporting device issues

Gerätefehler melden

If a device does not work as expected or a DP mapping is incorrect, the fastest route is the button below: it collects everything in one go — for every device the driver, the data point mapping, the live values and, where cloud credentials are stored, the manufacturer's specification, followed by the warnings and errors from the log.

Wenn ein Gerät nicht tut, was es soll, oder eine Datenpunkt-Zuordnung nicht stimmt, ist der Knopf unten der kürzeste Weg: er sammelt alles auf einmal ein — je Gerät den Treiber, die Datenpunkt-Zuordnung, die aktuellen Werte und, sofern Cloud-Zugangsdaten hinterlegt sind, die Spezifikation des Herstellers, gefolgt von den Warnungen und Fehlern aus dem Protokoll.

Which route to use. In the DP Debug tab, with a device selected, two buttons do the work for you. Report on GitHub opens a bug report with driver, versions, protocol and both data point tables already filled in — use it for a reproducible fault that needs fixing. Copy for forum puts a forum-ready post on the clipboard, folded into a collapsible block so it does not bury the thread, and opens the topic — use it for a question where other users may well know the answer, as several regulars there do. Pick one: the same report in both places splits the conversation.
Welchen Weg nehmen. Im Reiter DP-Debug nehmen Ihnen zwei Knöpfe die Arbeit ab, sobald ein Gerät gewählt ist. Auf GitHub melden öffnet einen Fehlerbericht, in dem Treiber, Versionen, Protokoll und beide Datenpunkt-Tabellen schon eingetragen sind — für einen nachstellbaren Fehler, der behoben gehört. Für das Forum kopieren legt einen fertigen Beitrag in die Zwischenablage, zusammengeklappt, damit er den Faden nicht zuschüttet, und öffnet das Thema — für eine Frage, auf die andere Benutzer die Antwort wissen könnten, und mehrere dort wissen sie. Nehmen Sie einen von beiden: derselbe Bericht an zwei Orten zerteilt das Gespräch.

Collected by hand, the same information comes from three places — one per tab. Useful to know if you only want to send part of it: the first two belong together and neither replaces the other, since one shows what the device does and the other what its data points mean.

Von Hand gesammelt stammen dieselben Angaben aus drei Quellen — je eine pro Reiter. Gut zu wissen, wenn Sie nur einen Teil schicken wollen: die ersten beiden gehören zusammen und ersetzen einander nicht, denn die eine zeigt, was das Gerät tut, und die andere, was seine Datenpunkte bedeuten.

  1. The DP specification — from Cloud Lookup. Cloud Lookup tab → Fetch Devices → Show DPs on the device's row → Copy Cloud DP Table. Gives the manufacturer's own name, the declared type and the allowed range for every data point. This is the only place that information exists — the local connection never transmits it.
  2. The live DP data — from DP Debug. DP Debug tab → select the device → Copy Local DP Table. This is what the device actually reports over the local connection. Operating the device with its own buttons or remote while watching the table shows which DP belongs to which function.
  3. The diagnostic log — from Logs. Logs tab → filter Warnings & Errors → Copy. Needed whenever a device disconnects, refuses commands or never connects at all; it distinguishes a network problem from a wrong DP mapping.
  1. Die DP-Spezifikation — aus der Cloud-Suche. Reiter Cloud-Suche → Geräte abrufen → DPs zeigen in der Zeile des Geräts → Cloud-DP-Tabelle kopieren. Liefert den Namen des Herstellers, den erklärten Typ und den erlaubten Bereich je Datenpunkt. Nur dort gibt es diese Angaben — die lokale Verbindung überträgt sie nie.
  2. Die tatsächlichen Werte — aus dem DP-Debug. Reiter DP-Debug → Gerät wählen → Lokale DP-Tabelle kopieren. Das ist, was das Gerät über die lokale Verbindung wirklich meldet. Bedienen Sie es mit seinen eigenen Tasten oder der Fernbedienung, während Sie die Tabelle beobachten — dann sehen Sie, welcher Datenpunkt zu welcher Funktion gehört.
  3. Das Diagnoseprotokoll — aus dem Protokoll. Reiter Protokoll → Filter Warnungen & Fehler → Kopieren. Wird gebraucht, sobald ein Gerät die Verbindung verliert, Befehle abweist oder gar nicht erst verbindet; es unterscheidet ein Netzproblem von einer falschen Datenpunkt-Zuordnung.

Together these give the DP numbers, types and value ranges of your specific model, plus what happened on the wire — enough to correct a mapping without owning the device. Post them on the community forum or as a GitHub issue, and please state the device brand and model plus what you expected to happen instead.

Zusammen ergeben sie die Datenpunktnummern, Typen und Wertebereiche genau Ihres Modells und dazu, was auf der Leitung geschah — genug, um eine Zuordnung zu berichtigen, ohne das Gerät zu besitzen. Stellen Sie das ins Community-Forum oder als GitHub-Meldung, und nennen Sie bitte Marke und Modell des Geräts sowie das, was Sie stattdessen erwartet hätten.

Safe to post publicly: none of these three copies identifies you. The DP tables carry the device name but no device ID, the log is labelled with device names only, and none of the three ever contains the Local Key. The support bundle is safe the same way: it shortens the device ID to six characters and replaces the key with asterisks.

One clipboard that is not safe: the Copy button on a row in Cloud Lookup deliberately copies the device ID and the Local Key, because that is what you need when adding a device by hand. Never paste that one into a forum post or a bug report — the key is the credential for the device.
Öffentlich unbedenklich: keine dieser drei Kopien verrät, wer Sie sind. Die DP-Tabellen tragen den Gerätenamen, aber keine Geräte-ID, das Protokoll ist nur mit Gerätenamen beschriftet, und in keiner der drei steht je der lokale Schlüssel. Das Supportpaket ist auf dieselbe Weise unbedenklich: es kürzt die Geräte-ID auf sechs Zeichen und ersetzt den Schlüssel durch Sternchen.

Eine Zwischenablage, die es nicht ist: der Knopf Kopieren in einer Zeile der Cloud-Suche kopiert absichtlich Geräte-ID und lokalen Schlüssel, denn genau das brauchen Sie, um ein Gerät von Hand anzulegen. Fügen Sie das nie in einen Forumsbeitrag oder einen Fehlerbericht ein — der Schlüssel ist der Zugang zum Gerät.
Three settings every device has. Auto-Reconnect Interval retries a device that is offline every N minutes (0 = off; the app reconnects on its own anyway, this is the safety net). Offline Grace is how long a device may be gone before the "disconnected" flow card fires — 60 seconds by default, because many of these devices drop the connection briefly and come back unprompted. Fire and forget sends commands without waiting for the device to acknowledge them; it is on by default where it has always been offered and off on thermostats, kettles, wall switches, doorbells and presence sensors, which never had the switch. Turn it on there if commands do not arrive, or if the device drops the connection immediately after one.
Drei Einstellungen, die jedes Gerät hat. Neuverbindungsintervall versucht es bei einem Gerät, das offline ist, alle N Minuten erneut (0 = aus; die App verbindet sich ohnehin von selbst wieder, dies ist das Netz darunter). Offline-Karenz ist die Zeit, die ein Gerät fehlen darf, bevor die Flow-Karte „getrennt“ auslöst — ab Werk 60 Sekunden, denn viele dieser Geräte lassen die Verbindung kurz fallen und kommen von allein zurück. Fire and forget schickt Befehle, ohne auf eine Bestätigung des Geräts zu warten; es ist dort eingeschaltet, wo es immer schon angeboten wurde, und ausgeschaltet bei Thermostaten, Wasserkochern, Wandschaltern, Türklingeln und Präsenzmeldern, die den Schalter nie hatten. Dort einschalten, wenn Befehle nicht ankommen oder das Gerät die Verbindung unmittelbar nach einem Befehl fallen lässt.

Fix It — automatic checks

Fix It — automatische Prüfungen

Most of what goes wrong with these devices is not a fault in the app but a setting that no longer matches the device: a local key that changed, a data point number written for a different model, a reading that is a hundred times off. Tuya publishes what each device actually has, so the Fix It tab compares your paired devices against that and offers to correct the differences.

Das meiste, was bei diesen Geräten schiefgeht, ist kein Fehler der App, sondern eine Einstellung, die nicht mehr zum Gerät passt: ein lokaler Schlüssel, der sich geändert hat, eine Datenpunktnummer, die für ein anderes Modell geschrieben wurde, ein Messwert, der um das Hundertfache danebenliegt. Tuya veröffentlicht, was jedes Gerät tatsächlich hat — der Reiter Fix It vergleicht Ihre angelernten Geräte damit und bietet an, die Unterschiede zu berichtigen.

Nothing is saved until you confirm. Every check runs as a preview first and lists exactly what it would change, device by device, old value to new value — and tells you why it left a device alone. Only then does a second button write anything.
Gespeichert wird erst, wenn Sie bestätigen. Jede Prüfung läuft zuerst als Vorschau und führt genau auf, was sie ändern würde, Gerät für Gerät, alter Wert zu neuem — und sagt, warum sie ein Gerät unangetastet liess. Erst danach schreibt ein zweiter Knopf etwas.

Zwei Dinge tut sie nicht. Sie erfindet nie einen Wert, den eine Einstellung nicht annimmt — ein Teiler ausserhalb des angebotenen Bereichs wird genannt, nicht gespeichert. If a check proposes something that looks wrong, do not apply it: copy the preview text into a forum post instead. It names the device, the setting and both values, which is everything needed to judge it.

Vier der fünf brauchen die Zugangsdaten der Cloud-Suche — richten Sie sie zuerst unter Cloud-Suche ein, eine einmalige Sache auf iot.tuya.com, beschrieben unter Erste Schritte. Schlägt eine Prüfung etwas vor, das falsch aussieht, wenden Sie es nicht an: kopieren Sie stattdessen den Vorschautext in einen Forumsbeitrag. Er nennt Gerät, Einstellung und beide Werte — alles, was zur Beurteilung nötig ist.

DP Instruction Mode

DP-Instruction-Modus

Tuya devices use the Standard Instruction Set by default, which translates commands into readable codes such as "switch_led". That works well for simple devices, but on more complex models it often gets in the way.

Tuya-Geräte benutzen ab Werk den Standard Instruction Set, der Befehle in lesbare Bezeichner wie "switch_led" übersetzt. Bei einfachen Geräten geht das gut auf, bei komplexeren steht es oft im Weg.

DP Instruction Mode switches to more direct, hardware-level communication. Three things it gives you:

Makes every function visible

Fixes third-party integrations

When a device is recognised in Homey, Home Assistant or TinyTuya but does not respond to anything, the standard mode is a frequent cause. Switching to DP Instruction Mode regularly resolves it.

A meter reports numbers and almost nothing else, and one number looks much like another: a voltage of 2376 and an energy total of 2376 are the same integer. So pairing guesses only what it can defend: the conventional block in the table above, and mains voltage where its value gives it away. That resolves six of the 42 meters in the catalogue that report each quantity separately. A wider table of numbers would reach twelve — and would confidently assign the wrong quantity on many of the rest, which is worse than reading nothing. The manufacturer’s code names do not move between models, and that is what Cloud Lookup supplies.
If a meter shows no readings, this is almost always why, and pairing now says so in the app log rather than leaving you to guess. Two ways out: save Cloud Lookup credentials and pair the device again, or open DP Debug, read which data point carries which reading, and enter the numbers in the device settings by hand. The second works without any cloud account at all.
Meters that pack a whole phase into one data point are not supported. Of the 70 meter definitions in the catalogue, 28 report voltage, current and power for a phase as a single binary value — 27 of them on data point 6. That format is undocumented, and no reading from a real device has been available to check an implementation against, so guessing at it would be worse than saying this plainly. Such a meter will pair and then show nothing. If you have one, a DP Debug capture is the thing to send.

Ceiling Fan Light — DP reference

For ceiling fittings that are a light with a fan in them: the Tuya combo families (categories fsd / xdd) and the equivalents from other brands. Use this driver rather than Fan when the fitting has a lamp — it is filed as a light, so it appears under Lights, joins light groups and answers “turn off all the lights on this floor”. A fan with no lamp belongs on the Fan driver.

Which half is which. The lamp is nearly always numbered below the fan on these fittings — 20 against 60, 20 against 107 — which is the opposite of what a fan-first guess would assume. Pairing therefore matches known pairs outright instead of picking the lowest data point. The three common layouts, counted across the 52 fan-with-light definitions catalogued by the tuya-local project:

107 / 20 107 switch, 106 mode, 105 speed, 104 direction 20–24 as above 5 models
Anything outside these is found by the value heuristic, and Cloud Lookup names the data points outright — that is the reliable route on an unusual fitting.
Fan speed. Most of these fittings run a 1–6 step scale, not a percentage: seventeen of the catalogued models declare 1–6 against four that declare 1–100. Pairing assumes steps unless the fitting is already reporting a speed above 6. If the speed slider does nothing, or only the bottom of it works, speed_max is the setting to correct — and Cloud Lookup fills in the declared range by itself.
Oscillation is not guessed. Only two of the 52 catalogued models have an oscillation data point at all, and a boolean says nothing about what it controls — guessing it produced toggles that cut the fan's power. Cloud Lookup resolves fan_horizontal, fan_vertical, shake, swing and fan_shake by name; otherwise set dp_oscillate by hand or leave it at 0.

Some chargers send everything as JSON. Instead of three packed phase blocks they write, on data point 102: {"L1":[2320,55,12],"L2":[2320,58,13],"L3":[2320,56,13],"t":370,"p":39,"d":54150,"e":113} — each phase is voltage, current and power in tenths of its unit, t the temperature and p the total power. It checks out against the charger itself: 232.0 V × 5.5 A is 1.28 kW against the 1.2 reported, the three phases add to 3.8 kW against the stated 3.9, and the vehicle said 4.1 kW at the same moment. Set DP Phase JSON and leave Phase A / B / C at 0.
d and e are not mapped, on purpose. Both have been tried as the session energy on the one charger that could be measured against its own app, and a later reading contradicted each of them. First e, because 113 matched the e=11.263kWh the charger writes out on a text data point. Then d, because 9010 and then 11410 as watt-hours ran towards a session that ended at 12.1 kWh. The third reading breaks both: idle, minutes after that same charge, the block read d=16800 and e=37, and across seven minutes d had grown by 3000 — more energy than a 16 A charger can deliver in that time, and far too fast to be seconds. Under no unit are these numbers consistent, so JSON session energy field defaults to none. Both raw values go to the Logs tab once; pick a field only after comparing against your own charger's app, and please report what you find.
Where the session energy really is. The same charger writes a record after every completed charge, on data point 105: {"t":"2026-09-20 15:09:32","s":"15:09","e":"17:42","d":9159,"c":121} — this is the only value on the device that can be checked rather than guessed, and it checks out three ways: s to e spans 9148 seconds, d counts 9159 (the same span to the second instead of the minute), and c of 121 is the 12.1 kWh the manufacturer's app showed for exactly that charge, after the 2 h 32 min d confirms. Set Charge History DP to it and the session tile is exact. It also settles the vocabulary: in this firmware d means duration, which is reason enough not to read the d next door as kilowatt-hours. Each record counts into the lifetime total once, identified by its timestamp, and the whole charge is added rather than a difference — a 12 kWh session followed by an 8 kWh one must add 8, where rising-counter arithmetic would have added nothing.
Charging power (target_power): Homey controls the charge rate in watts, which lets its energy management steer the charger — for example solar-surplus charging. The slider range follows your current_min / current_max settings: a 16 A single-phase charger becomes 0–3680 W in 230 W steps (1 A each). Anything below the charger's minimum current is treated as idle and stops the charge instead of requesting an impossible current.
Charging state mapping: Tuya reports eight states, Homey has five. charger_free and charger_free_fault → Not plugged in; charger_insert, charger_wait, charger_end and charger_fault → Plugged in; charger_charging → Charging; charger_pause → Paused. The exact Tuya state stays available through the "Detailed charger state changed" trigger and the matching condition, which can tell "waiting" from "finished".
Total energy: Many chargers expose a lifetime counter (DP 1) that reports a plausible value but never updates over the local connection. Because a single reading cannot tell a working counter from a frozen one, dp_energy_total stays at 0 and the total is accumulated from the session counter instead — which works on every model tested. If your charger's own counter does update, set dp_energy_total = 1.
Charging modes: Chargers usually advertise five modes (immediate, to %, fixed kWh, scheduled, delayed) but implement far fewer. On many units only Charge Now actually does anything. If switching modes has no effect, set dp_work_mode = 0 to hide the picker.

So neither is trusted: the driver reads the value and decides — a number is a percentage, a word is a level. A swapped pair still lands correctly, and the defaults only have to be plausible.
Polling is five minutes, not thirty seconds. A detector pushes its alarm the moment it sounds, so the poll only refreshes the battery reading, and on a cell-powered detector every request answered is battery spent.

The alarms use the monitor's own limits. Three of them are readable — CO2, CO and PM2.5 — and where one is, the matching alarm compares the measurement against it. The threshold stays the one set on the device rather than a second one kept in Homey, so changing it on the monitor changes it here too. Each needs its own measurement as well: the limit alone says nothing.
Temperature and humidity default to Automatic. Tuya specifies these monitors in tenths and the reported one sends whole degrees anyway, so the driver decides per reading: what cannot be a room temperature as a whole number is one in tenths, and a humidity above 100 can only be tenths of a percent.
Formaldehyde and TVOC are sent as µg/m³. Settled by reading one monitor against its own display: the display stood at 0.003 mg/m³ while the data point carried 3. A thousandth of a milligram is a microgram, which is the unit Homey charts — so nothing is converted, and nothing needs to be. Tuya still does not publish the unit, so the two scale settings stay for a monitor that disagrees with its own display.
Not read: the three alarm clocks and their switches, the sleep timer, the calibration counter, the display's own temperature unit, and the formaldehyde limit — Homey has no formaldehyde alarm to hang it on. They are all visible in DP Debug.

How learning works. Run Learn an IR code with a name; the card returns straight away rather than holding the flow open. Point the remote at the blaster from close up and press once. The code arrives, is saved under that name, and fires An IR code was learned — from then on Send an IR code offers it in a dropdown. A blaster left sitting in learning mode will not accept the next attempt, which is the usual reason a second try appears to do nothing; the driver leaves learning mode before entering it, so that repairs itself.
A damaged capture is not saved. A weak signal, a half-pressed button or a tired battery in the remote produce a code that stores perfectly well and never works. The container is checked instead — and learning stays on when one is refused, so pressing the button again is enough. What is kept gets a line in the Logs tab describing its shape, which needs no decoder and says a surprising amount: 160 durations, 431.7 ms, timing classes ~901 µs ×96, ~1814 µs ×56, ~30462 µs ×8. Two short classes at 1:2 are Manchester coding, so RC5 or RC6; a long lead-in then two short classes is NEC; the long class at the end is the gap between repeats of the frame.
The sensor is not always on 101 and 102. Some models put a display switch on DP 101 and their sensor elsewhere — the Woox R7246 uses DP 2 and DP 12. A true/false value on a reading's data point is ignored rather than read as 1, and reported once in the log, so a wrong guess shows up instead of appearing as a plausible one degree. Cloud Lookup finds the right numbers by name at pairing.
RF is not supported yet. The IR+RF models (Moes S11+, Avatto S16Pro and similar) send radio codes through the same data point but with a different command set, and a learned RF code is a different container — so this driver reads one as "not a usable IR code". It is a bounded piece of work, but there is no RF device here to test it against. If you have one, please report it: with one real capture it can be built properly rather than blind.

Troubleshooting

SymptomFix
Device stays unavailable Wrong IP, Device ID or Local Key — correct them in the device’s advanced settings; there is no separate repair screen. If only the key is stale, Fix It → Check local keys compares every device against your Tuya account and updates the ones that no longer match. Check the Logs tab for the exact error.
Devices stay offline after a router restart They should come back on their own: the app keeps retrying, waiting a little longer each time up to five minutes. If they only return when the app is restarted, update to 1.0.177 or later — before that, a device that accepted the connection but did not finish the protocol handshake left the app waiting forever, with nothing written to the log. To reconnect everything on a schedule or at the press of a button, use the flow action Reconnect devices; it covers all devices at once, and “offline devices only” leaves working ones alone.
Scan finds no devices Tuya devices only accept one TCP connection at a time. If the device is already added, the scan cannot reach it. Enter the IP address manually during pairing instead.
ECONNRESET on every connect Protocol version mismatch. The app retries the other versions by itself after five failed attempts — 3.3, 3.4, 3.1, 3.5 and 3.2 in that order; a few curtain motors are on 3.2, which is why the list does not stop at four. Once it is connected, Fix It → Check protocol versions stores the one that actually works, so the retry delay is not paid again on every reconnect. There is no "Auto-detect" choice in the device settings — that is offered only while pairing.
Connects, then never responds to anything Three causes in order of likelihood: (1) the IP belongs to a different device — Tuya devices show up as wlan0 / lwip1 in the router, so match by MAC from the Tuya app's Device info; (2) the device is on the Standard Instruction Set, which exposes only part of its data points — see DP Instruction Mode; (3) it has no local port at all — scan TCP 6668 and 6667, and if both are closed no setting will help.
