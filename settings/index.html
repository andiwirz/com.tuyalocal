Getting started

You need three things from each device: IP address, Device ID, and Local Key.

The Local Key changes every time you reset or re-pair a device in the Tuya / Smart Life app. If a device stops connecting, get the new key.

Getting the Device ID and Local Key

Use the Cloud Lookup tab (above) to fetch both directly from the Tuya IoT Platform — no CLI tools needed. Everything below is a one-time setup on Tuya's side; afterwards the tab lists every device in your Tuya account at the press of a button.

  1. On iot.tuya.com, create a free account, then Cloud → Create Cloud Project (Trial Edition is enough)
  2. In the project, Service API → Authorize: IoT Core and Authorization must be listed, otherwise every request fails with permission deny
  3. Link your devices: Devices → Link Tuya App Account → Add App Account → scan the QR code in the Tuya Smart / Smart Life app under Me → scan icon, top right
  4. Overview: copy your Access ID / Client ID and Access Secret / Client Secret
  5. Switch to the Cloud Lookup tab, paste your credentials, select the data center your Tuya account is registered in, and click Fetch Devices
  6. Use the Copy button to copy Device ID and Local Key
If lookup used to work and now fails, the free IoT Core trial has probably run out — it lasts about a month. Tuya reports this as No permissions. Your subscription to cloud development plan has expired. Extending is free but is an application, not a button: on iot.tuya.com go to Cloud → Cloud Services, find IoT Core in the list (its status reads Alerting shortly before it lapses) → View Details → My Subscriptions, then press Extend Trial Period next to the expiration date. The form asks for an extension period — pick 6 months, the longest offered — plus your developer identity, the estimated number of devices, a short project description and contact details. Tuya states that applications are approved within one to two working days, so lookup keeps failing until then. Nothing in Homey needs changing afterwards.
The data center trap. A free Tuya account is locked to one data center: whichever you pick for your first project applies to every project on that account, and changing it means deleting all projects and starting over. Worse, the choice is partly made for you — accounts registered in some countries (the UK among them) are assigned Western Europe and cannot select Central Europe at all, however the region is set. If your Smart Life account sits in a region your project cannot reach, no combination of settings here will find your devices. The way out reported by users who hit this: create a fresh Tuya account registered in a region where all data centers are offered, then link Smart Life to a project under that account. If you are starting over anyway, deleting the old empty projects first avoids inheriting the locked choice.

Cloud-assisted DP detection

Once your Cloud Lookup credentials have been saved here, pairing gets noticeably more accurate. The local connection only ever sees raw DP numbers and values, so the app has to guess what each one means from the value shape. The cloud specification instead supplies the manufacturer's own name per DP — envhumid, windspeed, work_state, bright_value and so on — which is matched directly.

This mainly helps devices whose enums use plain numbers (0 / 1) instead of names, where value-shape guessing has nothing to go on, and it reads the full list of allowed values for mode and fan-speed pickers rather than just the one value the device happens to be reporting at that moment. It is entirely optional — pairing works without it, you may just have to correct a few DP numbers by hand afterwards.

Enum values are matched exactly

Mode and fan-speed settings hold the tokens the device itself uses, and the comparison is literal — case included. A device whose modes are Heat,Cool,Auto rejects heat,cool,auto, and the symptom is deceptive: the command appears to go through, then the device snaps straight back to its previous mode. Devices seen in the wild use cold,wet,wind,hot instead of cool/dry/fan/heat, or bheat,eheat,sheat,bcool,ecool,scool,auto for boost/eco/silent variants. Read the exact tokens from the DP specification in Cloud Lookup and copy them verbatim into mode_values / fan_speed_values. With Cloud Lookup credentials saved this is filled in automatically at pairing.

Find the IP address

Use Scan Network in the pairing wizard, or check your router's DHCP table. Either way, assign a static IP / DHCP reservation so it never changes.

Matching an IP to the right device is the harder half. Tuya devices report almost no hostname: older ESP-based ones appear as ESP_ plus the last six characters of their MAC, newer ones as wlan0, and the newest as lwip1 — so eight devices show up as eight identical wlan0 entries. Take the MAC address from the Tuya / Smart Life app under the device's Device info and match on that. Assigning the wrong IP produces a device that connects to something and then never responds.

The scan works in two passes: it first listens six seconds for the announcements Tuya devices broadcast by themselves (UDP 6666/6667), then probes every address in your subnet on TCP 6668. On a normal home network that takes around ten seconds. The second pass is skipped on subnets larger than 2046 addresses, where probing every host would take minutes — devices there are only found if they announce themselves.

Can this device be controlled locally at all?

Worth two minutes before spending an evening on settings. Local control needs the device to be listening on TCP 6668 (occasionally 6667). Point any port scanner — Advanced Port Scanner, a phone network-analyser app, nmap — at the device's IP and check those two ports.

Open means the device speaks the local protocol and any failure from here is a matter of key, protocol version or DP mapping. Both closed means it does not, and nothing in this app can change that — some devices sold as Tuya are Matter or cloud-only under the hood and simply have no local port. Users have chased such a device for weeks before running this check.

Known to be impossible locally, whatever the settings say:
  • Battery sensors in deep sleep — door, motion, smoke, temperature/humidity sensors switch their radio off between reports. There is no window in which to connect, and the cloud sees them only because the device pushes to Tuya itself.
  • Bluetooth devices behind a Tuya gateway — the gateway proxies them to the cloud, not over the local protocol, and most models accept only one to three connections in total.
  • Cameras and video doorbells — the video stream is a proprietary peer-to-peer protocol. Ring and motion events over the local connection can work; the picture cannot. For the stream, use an ONVIF app if the device supports it.

Reporting device issues

If a device does not work as expected or a DP mapping is incorrect, the fastest route is the button below: it collects everything in one go — for every device the driver, the data point mapping, the live values and, where cloud credentials are stored, the manufacturer's specification, followed by the warnings and errors from the log.

Which route to use. In the DP Debug tab, with a device selected, two buttons do the work for you. Report on GitHub opens a bug report with driver, versions, protocol and both data point tables already filled in — use it for a reproducible fault that needs fixing. Copy for forum puts a forum-ready post on the clipboard, folded into a collapsible block so it does not bury the thread, and opens the topic — use it for a question where other users may well know the answer, as several regulars there do. Pick one: the same report in both places splits the conversation.

Collected by hand, the same information comes from three places — one per tab. Useful to know if you only want to send part of it: the first two belong together and neither replaces the other, since one shows what the device does and the other what its data points mean.

  1. The DP specification — from Cloud Lookup. Cloud Lookup tab → Fetch Devices → Show DPs on the device's row → Copy Cloud DP Table. Gives the manufacturer's own name, the declared type and the allowed range for every data point. This is the only place that information exists — the local connection never transmits it.
  2. The live DP data — from DP Debug. DP Debug tab → select the device → Copy Local DP Table. This is what the device actually reports over the local connection. Operating the device with its own buttons or remote while watching the table shows which DP belongs to which function.
  3. The diagnostic log — from Logs. Logs tab → filter Warnings & Errors → Copy. Needed whenever a device disconnects, refuses commands or never connects at all; it distinguishes a network problem from a wrong DP mapping.

Together these give the DP numbers, types and value ranges of your specific model, plus what happened on the wire — enough to correct a mapping without owning the device. Post them on the community forum or as a GitHub issue, and please state the device brand and model plus what you expected to happen instead.

Safe to post publicly: none of these three copies identifies you. The DP tables carry the device name but no device ID, the log is labelled with device names only, and none of the three ever contains the Local Key. The support bundle is safe the same way: it shortens the device ID to six characters and replaces the key with asterisks.

One clipboard that is not safe: the Copy button on a row in Cloud Lookup deliberately copies the device ID and the Local Key, because that is what you need when adding a device by hand. Never paste that one into a forum post or a bug report — the key is the credential for the device.
Three settings every device has. Auto-Reconnect Interval retries a device that is offline every N minutes (0 = off; the app reconnects on its own anyway, this is the safety net). Offline Grace is how long a device may be gone before the "disconnected" flow card fires — 60 seconds by default, because many of these devices drop the connection briefly and come back unprompted. Fire and forget sends commands without waiting for the device to acknowledge them; it is on by default where it has always been offered and off on thermostats, kettles, wall switches, doorbells and presence sensors, which never had the switch. Turn it on there if commands do not arrive, or if the device drops the connection immediately after one.

Fix It — automatic checks

Most of what goes wrong with these devices is not a fault in the app but a setting that no longer matches the device: a local key that changed, a data point number written for a different model, a reading that is a hundred times off. Tuya publishes what each device actually has, so the Fix It tab compares your paired devices against that and offers to correct the differences.

Nothing is saved until you confirm. Every check runs as a preview first and lists exactly what it would change, device by device, old value to new value — and tells you why it left a device alone. Only then does a second button write anything.

DP Instruction Mode

Tuya devices use the Standard Instruction Set by default, which translates commands into readable codes such as "switch_led". That works well for simple devices, but on more complex models it often gets in the way.

DP Instruction Mode switches to more direct, hardware-level communication. Three things it gives you:

Makes every function visible

Many Tuya devices have extra modes, timers, scenes or sensor readings that the standard mode never exposes. DP mode unlocks all available DPs — ideal for Tuya Local, because you can then map every function cleanly.

Fixes third-party integrations

When a device is recognised in Homey, Home Assistant or TinyTuya but does not respond to anything, the standard mode is a frequent cause. Switching to DP Instruction Mode regularly resolves it.

Direct hardware control

Instead of textual commands, plain DP numbers and values are sent:

{"21": "scene"}

That is more robust on devices which do not follow the Tuya standard exactly.

🔧 How to enable it

The change is made on the Tuya IoT Developer Platform, not in Homey:

  1. Sign in to the Tuya Developer Platform
  2. Cloud → Development in the left menu, then open your project
  3. Open the project's Devices tab and stay on All Devices
  4. Under View Devices by Product find the card for your device's product — it shows the device count and the mode currently in force, normally Standard Instruction
  5. Hover that card and click the pencil icon; its tooltip reads Change Control Instruction Mode
  6. On the Configure Control Instruction Mode screen pick the DP Instruction card, then press Save Configuration — the choice is not applied until you save

That screen also carries the Table of Instructions, listing the DP instructions against the standard ones side by side. It is worth a look before saving: the difference in length is exactly what you gain.

The warning Tuya shows is real. Saving asks you to confirm that the devices under the project “might not be able to be controlled by the original standard instructions”. Anything that drives these devices through standard instructions can stop working — the official Tuya cloud app, or voice assistants wired up that way. Users have switched a curtain motor to DP Instruction and found it dead in the cloud integration while the Smart Life app kept working. Local control through this app is unaffected, and the switch is reversible on the same screen.
Scope: the setting applies to one product within one project — every device of that product in that project switches with it, other products do not. Because it changes what the cloud exposes, re-run Fetch Devices in the Cloud Lookup tab afterwards to see the full DP list.

Temperature scaling: Most dehumidifiers send the temperature multiplied by 10 (e.g. 220 = 22.0 °C), which is why temp_divisor defaults to 10. If the reading comes out 10× too low, the device sends whole degrees — set temp_divisor = 1.
Numeric mode / fan-speed values: Some dehumidifiers report modes and fan speeds as plain numbers ("0", "1") instead of names like auto or low. Set mode_values = 0,1 and fan_speed_values = 0,1 to match, otherwise the picker rejects the values and the tiles stay empty.
Timer format: Two settings cover the common deviations. Enable Timer uses plain numbers if the timer DP sends 0…24 rather than cancel / 1h … 24h. Enable Timer Remaining DP is in minutes if the remaining-time DP counts minutes (0–1440) rather than hours.
Water tank alarm: On many models this DP is really a fault bitmap covering several error conditions, not a dedicated tank sensor. The driver treats any non-zero value as "tank full", so an unrelated fault can surface as a tank alarm. Watch the raw value in DP Debug while filling the tank to confirm which value your device actually uses.

That resolves six of the 42 meters in the catalogue that report each quantity separately. A wider table of numbers would reach twelve — and would confidently assign the wrong quantity on many of the rest, which is worse than reading nothing. The manufacturer’s code names do not move between models, and that is what Cloud Lookup supplies.
If a meter shows no readings, this is almost always why, and pairing now says so in the app log rather than leaving you to guess. Two ways out: save Cloud Lookup credentials and pair the device again, or open DP Debug, read which data point carries which reading, and enter the numbers in the device settings by hand. The second works without any cloud account at all.
Meters that pack a whole phase into one data point are not supported. Of the 70 meter definitions in the catalogue, 28 report voltage, current and power for a phase as a single binary value — 27 of them on data point 6. That format is undocumented, and no reading from a real device has been available to check an implementation against, so guessing at it would be worse than saying this plainly. Such a meter will pair and then show nothing. If you have one, a DP Debug capture is the thing to send.

Ceiling Fan Light — DP reference

For ceiling fittings that are a light with a fan in them: the Tuya combo families (categories fsd / xdd) and the equivalents from other brands. Use this driver rather than Fan when the fitting has a lamp — it is filed as a light, so it appears under Lights, joins light groups and answers “turn off all the lights on this floor”. A fan with no lamp belongs on the Fan driver.

Which half is which. The lamp is nearly always numbered below the fan on these fittings — 20 against 60, 20 against 107 — which is the opposite of what a fan-first guess would assume. Pairing therefore matches known pairs outright instead of picking the lowest data point. The three common layouts, counted across the 52 fan-with-light definitions catalogued by the tuya-local project:
LayoutFanLightSeen on
60 / 20 60 switch, 61 mode, 62 speed, 63 direction 20 switch, 21 mode, 22 brightness, 23 colour temp, 24 colour 16 models
1 / 9 or 15 1 switch, 2 mode, 3 speed, 8 direction 9 or 15 switch, 10 or 16 brightness, 17 colour temp 12 models
107 / 20 107 switch, 106 mode, 105 speed, 104 direction 20–24 as above 5 models
Anything outside these is found by the value heuristic, and Cloud Lookup names the data points outright — that is the reliable route on an unusual fitting.
Fan speed. Most of these fittings run a 1–6 step scale, not a percentage: seventeen of the catalogued models declare 1–6 against four that declare 1–100. Pairing assumes steps unless the fitting is already reporting a speed above 6. If the speed slider does nothing, or only the bottom of it works, speed_max is the setting to correct — and Cloud Lookup fills in the declared range by itself.
Oscillation is not guessed. Only two of the 52 catalogued models have an oscillation data point at all, and a boolean says nothing about what it controls — guessing it produced toggles that cut the fan's power. Cloud Lookup resolves fan_horizontal, fan_vertical, shake, swing and fan_shake by name; otherwise set dp_oscillate by hand or leave it at 0.

The settings are the same fields as on the Fan driver, with one difference in where they land: here dp_light_onoff drives the tile's main switch and dp_light_dim its brightness slider, while dp_onoff and dp_speed become the secondary Fan switch and Fan speed.

Driver for Tuya WiFi access control panels with face, fingerprint, card and code entry (category mk). Read the note below before expecting too much of it: most of what these panels do cannot be reached locally at all.

What this driver cannot do, and why. Of the 37 data points on the panel it was built for, 25 are Raw — an undocumented binary format. The undecodable data points are still usable. The flow trigger A specific data point changed fires for one data point of your choosing and hands you its raw value, so the parts this app cannot interpret become something you can build on. The unlock records are the useful case: each enrolled person produces a different value, so unlock the door yourself once, read the value off the trigger, and from then on a comparison against it tells you who is at the door. Locking from Homey is off until you switch it on. Two reasons, and both are about a door rather than a lamp. Troubleshooting

SymptomFix
Device stays unavailable Wrong IP, Device ID or Local Key — correct them in the device’s advanced settings; there is no separate repair screen. If only the key is stale, Fix It → Check local keys compares every device against your Tuya account and updates the ones that no longer match. Check the Logs tab for the exact error.
Devices stay offline after a router restart They should come back on their own: the app keeps retrying, waiting a little longer each time up to five minutes. If they only return when the app is restarted, update to 1.0.177 or later — before that, a device that accepted the connection but did not finish the protocol handshake left the app waiting forever, with nothing written to the log. To reconnect everything on a schedule or at the press of a button, use the flow action Reconnect devices; it covers all devices at once, and “offline devices only” leaves working ones alone.
Scan finds no devices Tuya devices only accept one TCP connection at a time. If the device is already added, the scan cannot reach it. Enter the IP address manually during pairing instead.
ECONNRESET on every connect Protocol version mismatch. The app retries the other versions by itself after five failed attempts — 3.3, 3.4, 3.1, 3.5 and 3.2 in that order; a few curtain motors are on 3.2, which is why the list does not stop at four. Once it is connected, Fix It → Check protocol versions stores the one that actually works, so the retry delay is not paid again on every reconnect. There is no "Auto-detect" choice in the device settings — that is offered only while pairing.
Connects, then never responds to anything Three causes in order of likelihood: (1) the IP belongs to a different device — Tuya devices show up as wlan0 / lwip1 in the router, so match by MAC from the Tuya app's Device info; (2) the device is on the Standard Instruction Set, which exposes only part of its data points — see DP Instruction Mode; (3) it has no local port at all — scan TCP 6668 and 6667, and if both are closed no setting will help.
Mode or preset command snaps back immediately The value list does not match the device's own tokens, and matching is case-sensitive: a device using Heat,Cool,Auto rejects heat,cool,auto. Copy the tokens verbatim from the DP specification in Cloud Lookup into mode_values, then restart the app.
Battery sensor never connects Battery-powered sensors keep their radio off between reports, leaving no window to connect. They cannot be used locally — only through the cloud, where the device pushes by itself.
Smart Plug values are 10× off Incorrect DP numbers or wrong power scale — adjust in device settings.
Energy (kWh) never updates Set dp_energy = 0 — app computes kWh from power readings.
AC / Heater temperature is 10× too high Set temp_divisor = 10 in device settings.
AC mode / fan picker shows wrong options Update mode_values / fan_speed_values in device settings to match what your device sends, then restart the app.
AC swing picker shows wrong options Update swing_values (e.g. off,on,updown) to match what the device sends. Check DP Debug while toggling swing manually.
Picker still shows old options after edit Restart the Tuya Local app to clear Homey's capability cache.
Fan direction not detected at pairing Set dp_direction manually in device settings (e.g. DP 63). Values must be forward / reverse.
Light color mode not switching Check the DP Debug tab while switching modes manually to find the exact strings, then update color_mode_white_val / color_mode_color_val in device settings.
Light brightness or color temp range is wrong Adjust brightness_max or color_temp_max in device settings (default 1000; some older devices use 255).
Humidifier water alarm fires on connect Built-in debounce suppresses transient alarms. If they persist, check the Logs tab for the DP value and timing.
Spurious water / fault alarm after reconnect Built-in debounce suppresses these. If they persist, check the Logs tab for the exact DP value and timing.
Garage door shows wrong open/closed state Enable door_contact_invert in device settings to swap the reading. Or set dp_door_contact to the correct DP number using the DP Debug tab.
Garage door Stop action has no effect WOFEA DP 6 ignores "stop" — use Toggle garage door instead (sends a relay pulse on dp_switch). For BoboYun set dp_switch = 103.
Garage door open/close action doesn't work (BoboYun) BoboYun uses separate open/close DPs. Set dp_door_open = 106 and dp_door_close = 107 in device settings.
Garage door alarm never fires (BoboYun) BoboYun alarm DP 141 is not auto-detected. Set dp_door_state = 141 manually in device settings after pairing.
AOSD light not controllable Set dp_light = 105 in device settings (auto-detected at pairing, but verify in DP Debug tab).
Heat pump mode picker does nothing after enabling dp_mode Restart the Tuya Local app — the capability listener is registered at startup. Future changes re-register automatically without a restart.
Heat pump temperature is wrong or 10× off Set temp_divisor to 10 if the device sends temperatures ×10 (e.g. 350 for 35 °C), or to 100 for two decimal places (2750 = 27.50 °C). Auto-detected at pairing for most devices, and Fix It → Check measurement scaling can read it from the specification. Heat pumps have a second divisor, current_temp_divisor, for when the measured temperature is scaled differently from the target.
Heat pump target temp correct but measured temp is 10× too high Asymmetric DP scaling (e.g. Weau): set current_temp_divisor = 10 in device settings and leave temp_divisor = 1. Set to 0 to fall back to temp_divisor.
Heat pump spurious fault alarm on connect Built-in 30 s grace period suppresses transient faults after reconnect. If alarms persist longer, check the Logs and DP Debug tabs.
Doorbell ring trigger doesn't fire Check that dp_doorbell matches the DP your device uses (common: 136). Use the DP Debug tab while pressing the bell to identify the correct DP. Some devices use base64 on DP 185 — set dp_alarm_message = 185 instead.
Doorbell motion trigger fires on connect Seed protection suppresses the first packet after every (re)connect. If false triggers persist, check the DP Debug tab — the device may be sending motion=true as its idle state.
Doorbell flow action throws "DP is set to 0" error The action requires the corresponding DP to be configured. Set dp_motion_switch, dp_nightvision, dp_chime_volume, or dp_motion_sensitivity to the correct DP number in device settings.
Curtain position slider is inverted (0% = open) Enable invert_position in device settings to swap the direction.
Curtain motor doesn't stop at the right position The motor limit positions are set in the Tuya / Smart Life app (DP 16 border calibration), not in Homey. Run the limit calibration from the original app first.
Curtain tile shows "moving" but motor has stopped The work_state DP may not be resetting to idle on your device. Set dp_work_state = 0 to disable it — the tile state will then follow the control DP echo instead.
Device missing DPs or commands rejected Your device may be using the Standard Instruction Set, which hides some DPs. Switching to DP Instruction exposes all raw DPs with full read/write access — see DP Instruction Mode for the click path.
Cloud Lookup shows fewer DPs than expected Same cause — the Standard Instruction Set limits what the cloud API returns. Switch to DP Instruction Mode, then re-fetch in Cloud Lookup.
SET command causes disconnect 1) Refresh Local Key via Cloud Lookup. 2) Enable Fire and Forget in device settings. 3) Try Protocol 3.4. 4) Switch to DP Instruction Mode.
Device goes offline after a while and never recovers Set Auto-Reconnect Interval back to 0 or a few minutes. It only reconnects while the device is genuinely offline and has no effect on a healthy connection.
Mode or fan-speed tile stays empty The device reports values that are not in the picker's list. Check the raw value in DP Debug, then set mode_values / fan_speed_values to match exactly (numeric devices need e.g. 0,1) and restart the app.
Newly enabled tile does not respond to taps Fixed as of v1.0.129 for the Fan and Dehumidifier drivers — capabilities enabled through device settings are now controllable immediately. On other drivers, restart the Tuya Local app once.
Generic picker shows raw numbers instead of labels Add a readMap to that DP's entry in dp_config, with the raw values as text keys: {"0":"Auto","1":"Continuous"}.
EV charger total energy never increases Leave dp_energy_total at 0 so the total is accumulated from the session counter. Many chargers expose a lifetime counter that never updates over the local connection.
EV charger power slider range looks wrong Set current_min / current_max to your charger's real amp range and Phases to 1 or 3. The watt range is derived from those (W = A × V × phases).
EV charger shows no voltage / current / power Some chargers only stream live measurements while their online_state DP is set to online. Set dp_live_updates = 27 — the app then re-asserts it on every reconnect.
EV charging mode picker has no effect Most of these chargers advertise modes they do not implement; only "Charge Now" tends to work. Set dp_work_mode = 0 to hide the picker.

Fix It

Checks your paired devices against the manufacturer's own specification and offers to correct what does not match.

Nothing here saves anything until you confirm: each check shows exactly what it would change, per device, and says why a device was left alone. All except protocol versions need Cloud Lookup credentials — enter them under Cloud Lookup first.

Create support bundle
Collects everything about every device in one go — the driver, the data point mapping, the live values, the connection history and the warnings from the log. Send it with a report, or read it yourself: it puts what a device is actually sending next to what the app expects, which is where most faults become obvious. Local keys never appear in it and device IDs are shortened, so it is safe to share.
Where to send it: Help → Reporting device issues.
Check local keys
A device's local key changes every time it is reset or re-paired in the Tuya app, and the symptom is a device that never connects again. This compares the stored key with the one your Tuya account holds now. The account is the authority here, so there is no guesswork. Keys are shown shortened, never in full — a local key is the credential for the device, and this page ends up in screenshots.
Check protocol versions
When the configured protocol version keeps failing, the app tries the others and carries on with whichever works — so a device can run fine on 3.3 while its settings still say 3.4. It costs the retry delay on every reconnect: five failed attempts before the working version is reached again. This stores the version actually in use. Only devices connected right now can be judged, and no Cloud Lookup credentials are needed.
Check measurement scaling
Devices report whole numbers, and the manufacturer states how to scale them — raw 2301 means 230.1 V. Pick the wrong factor and voltage, current, power or the energy meter read ten or a hundred times off. This reads the declared factor instead of leaving you to work it out. A factor this app does not offer as a choice is reported, not written.
Update pickers on existing devices
Reads the manufacturer's declared mode, fan speed, preset and status options for your paired devices. Useful when a picker shows names your device does not understand, or plain numbers. Where a data point's own numeric span is declared, this also corrects a brightness or colour-temperature setting still assuming a 0–100 scale it does not use. Nothing is saved until you confirm: the preview lists every change first. Data point numbers are left exactly as they are, and nothing is ever switched off.
Find data points your device does not have
Driver defaults are written for one device family and can point at nothing on another — a wireless chime carrying a camera doorbell's defaults shows a motion tile and a night-vision switch that can never work. A number is only reported here when the manufacturer's specification does not list it and your device has never once reported it. Nothing is saved until you confirm.
